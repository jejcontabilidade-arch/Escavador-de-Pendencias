## 🏗️ Planejamento & Arquitetura

### 🎙️ Arquitetura de Voz e NLP (WhatsApp)
A captação de mensagens de voz é executada na camada do gateway Node.js (`whatsapp-web.js`), que detecta mídias dos tipos de áudio e as baixa nativamente. Para manter o gateway leve e centralizar a segurança e chaves de API, os bytes do áudio são repassados ao Flask em Base64.
No backend Python, a transcrição é feita de forma desacoplada chamando a API Whisper da OpenAI (`whisper-1`) em português. O texto retornado atualiza a variável principal da mensagem, permitindo que todo o ecossistema NLP preexistente (GPT-4o-mini e heurísticas locais) interprete o comando de voz exatamente como se fosse um texto digitado.

### 📊 Consolidação de Dados sob Demanda
Anteriormente, as planilhas consolidadas eram atualizadas apenas ao término da execução completa dos robôs. Desenvolvemos uma arquitetura de consolidação sob demanda: as funções em `rebuild_utils.py` lêem os arquivos físicos locais de status (`status.json` e `status_nota_fiscal_xml.json`) e os arquivos baixados para reconstruir as planilhas premium em tempo de execução. Isso permitiu integrar a reconstrução tanto no webhook do WhatsApp (enviando a planilha atualizada na hora) quanto no clique de download do painel web.

### 📝 Centralização no Certificado Contábil e Parser XML-JSON
Para a automação de NF-e XML, o fluxo foi alterado de consultas cliente-a-cliente para uma consulta concentrada usando o certificado contábil centralizado da J&J Contabilidade (`05443435000124`). O robô agora percorre as chaves de acesso informadas, e caso o arquivo XML já exista no disco (bypass de redundância), ele executa apenas a rotina de parser local para gerar o JSON, sem consumir tempo de rede ou requisições de Captchas adicionais na SEFAZ. O JSON é gravado de forma limpa, recursiva e tipada para facilitar conciliações futuras em outros robôs.

### 7. Resiliência, Loop de Confirmação e Prevenção de Travamentos por TLS (`executar.py` e `consultar_nota_fiscal_xml.py`)
Investigamos com scripts de testes automáticos independentes o travamento do login em ambos os sistemas e solucionamos dois comportamentos críticos do Windows/Chrome:
* **Invisibilidade do Diálogo de Certificado do Chrome**: Descobrimos via listagem de HWNDs do SO que o diálogo *"Selecione um certificado"* é desenhado internamente pelo Chrome e não aparece como uma janela separada do Windows para a API `EnumWindows`. Removemos a checagem que exigia a existência dessa janela separada. Agora, a thread paralela traz a janela principal do próprio navegador (`keywords_browser`) para o Foreground de forma garantida.
* **Envio Periódico e Temporizado**: A thread `executar_confirmacao_certificado_em_loop` agora aguarda 3.5 segundos fixos após o clique (tempo para o navegador processar e abrir o diálogo SSL interno) e executa 3 tentativas de focar no navegador e simular a seleção (tecla *"J"*) e o *"ENTER"*. Isso elimina totalmente qualquer falso negativo ou timeout no SO.
* **Bypass de Congelamento TLS do Playwright**: Ao clicar no link de "Manifestação Destinatário" ou no botão "Seu certificado digital", o navegador congela na negociação SSL de cliente e trava a thread principal do Playwright, resultando em timeouts generalizados. Protegemos esses cliques com blocos `try-except` e timeouts curtos de 5 segundos (`timeout=5000`), liberando a thread principal do Python para aguardar o painel pós-login de forma assíncrona.
